## 2026-05-31: Measure before claiming a metric is bad
**Lesson:** Do not assert a quantitative gap from architecture prose. Measure it. In the v4 review this session, I claimed cache hit rate was "effectively zero" and "unmeasured." When `scripts/session_cost.py` was built and run, the Anthropic prompt cache was at 92.2% across 31 sessions (95.6% this session). The real gap was the absence of *measurement* and of a *local Notion cache for cold start*, not a low hit rate. I had conflated two different caches (the automatic prompt cache vs the planned local index cache).
**Rule:** Before stating any number-shaped weakness ("X is slow / zero / expensive"), build or run the measurement first. An unmeasured metric is "unknown," never "bad."
**Evidence:** `python scripts/session_cost.py --all` output, 2026-05-31, TOTAL hit_rate 92.2% over 8,583 messages.

## 2026-05-31: A linter must pass its own gate
**Lesson:** The first `em_dash_lint.py` failed on its own source (the banned characters were typed as literals) and crashed printing them on a cp1252 console. Building the needles from `chr(0x2014)` and forcing UTF-8 output fixed both. The generator also emitted em dashes into the cache via mirrored third-party skill descriptions, fixed by sanitizing mirrored text.
**Rule:** A tool that forbids a token must contain none of it as a literal (construct from code points), and must sanitize any external text it republishes. Dogfood every gate against its own outputs.
**Evidence:** `evals/em_dash_lint.py --selftest` PASS; full gate over spine files exit 0, 2026-05-31.

## 2026-06-01: A review standard is a skill, not a persona agent; build behind a scope gate
**Lesson:** Asked whether to create a celebrity-named "Karpathy" review agent, the right answer was no. The judgment a review needs already comes from whatever model runs it; the durable, ownable artifact is the rubric (the checklist of what a great engineer checks for). By the v4 litmus (loops and decides, equals agent; knowledge applied on demand, equals skill), a review standard is a skill. A named persona would be costume over a rubric and would add an agent against the "few agents, many shared skills" and "deprecate the dead" rules. The independence that makes review valuable comes from running the skill in a FRESH context (a reviewer subagent), not from a new agent type. Built `skills/engineering-review/SKILL.md` with two gates: Gate 1 is the scope/YAGNI filter (does this serve the cold start, is it needed now and not for a fleet we do not run, is it the leanest option, did Asma actually ask for it) applied BEFORE any code-quality judgment; Gate 2 is the engineering pass. The scope gate exists because the failure mode Asma most wants caught is Claude automating things she does not need.
**Rule:** Default new capabilities to skills; only create an agent when it names a distinct look-decide-act loop an existing agent plus a skill cannot do. Review work in a fresh context so it cannot rubber-stamp itself. Run every infra build through Gate 1 (scope) before Gate 2 (quality): well-built but unneeded is still a fail.
**Evidence:** `skills/engineering-review/SKILL.md`; fresh-context review of item A (crash-resume) returned Gate 1 PASS (lean, anchored, uses Claude Code primitives) plus 5 Gate 2 hardening fixes; LinkedIn diagrams `images/2026-06-01/os-diagrams/skills-vs-agents.png` and `review-is-a-skill-scope-gate.png`.

## 2026-06-01: Surface and document the coding principles, do not apply them silently
**Lesson:** Asma asked that the engineering principles behind the build always be stated and documented, because for a teachable 2-person OS the principles are as valuable as the code. The principles this session (each with this session's evidence): (1) Optimise the cold start, build for token-zero competence (the resume banner + kernel injection). (2) Build only what we need, the YAGNI scope gate runs before any code judgment (engineering-review Gate 1). (3) Prove it, do not claim it, every build ships an eval that runs (`crash_resume_eval` PASS). (4) Fail safe, a hook never breaks the session it runs in (every script exits 0 on error). (5) Portable by default, no machine paths, `python3`, Windows + Mac. (6) Review in a fresh context, no self-rubber-stamp (the reviewer subagent). (7) Right rule, right layer, content gates apply to content not code (the em-dash gate was scoped to prose file types only, per Asma's call that the ban is content-writing only).
**Rule:** In any infra/code turn, name the principles in plain language and record consolidated ones here with evidence. The canonical rubric is `skills/engineering-review/SKILL.md`.
**Evidence:** `skills/engineering-review/SKILL.md`; `evals/em_dash_lint.py` CONTENT_SUFFIXES scoping (commit 8e4f550); diagram `images/2026-06-01/os-diagrams/engineering-principles.png`.

## 2026-06-01: Know the context budget, stop before quality drops, flag the limit
**Lesson:** Asma asked for context self-awareness as a first-class operating rule: a long session degrades quality (a model has a finite attention budget, and an overfull window loses the middle, the "lost in the middle" effect in v4). The discipline is to judge remaining context honestly, do the bounded low-risk work while quality is high, and STOP before the work that needs careful fresh-context grounding (e.g. anything that must be grounded in a source without inventing, like agents grounded in the EDITORIAL-BIBLE). A clean handoff beats a degraded push. Alert Asma when context threatens quality rather than pushing past it silently.
**Rule:** Track context use across a session. Sequence bounded/low-grounding tasks late and high-grounding tasks while fresh. When approaching the zone where quality would drop, say so and offer a clean wrapup/handoff instead of continuing. This is the 8th coding principle, added to the set above.
**Evidence:** This session (A + B + review + 4 diagrams + gate fix) ran long; flagged the limit and deferred the deep-grounding agent items (C-agent, E) rather than degrade them. Diagram `images/2026-06-01/os-diagrams/context-budget.png`.
